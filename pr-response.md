## Comment 4 — Default visibility
**My position:** I changed `WatchlistEntry.public` from defaulting to `True` to defaulting to `False`. I'm pushing back on `@Samiz244`'s rationale for keeping `public=True` — I think it's the wrong default for CineLog *right now*, even though I don't think the reasoning behind it is unreasonable in the abstract.

**Reasoning:** `@Samiz244`'s argument for `public=True` is that it "creates a social, community-driven user discovery workflow" and "minimiz[es] user friction by allowing friends and followers to instantly discover saved films without requiring any manual privacy toggles." That argument only pays off if there's somewhere for that discovery to happen. I went through the rest of the codebase looking for it: `routes/films.py`, `routes/collection.py`, and `routes/watchlist/watchlist.py` are the entire public API surface, and none of them expose any other user's data: there's no `/users/<id>/profile`, no followers/friends model on `User` in `models.py`, and no endpoint that lets one user browse another user's watchlist or collection. `GET /watchlist/<user_id>` requires already knowing the exact `user_id` you're looking up. So today, setting `public=True` doesn't create discoverability. CineLog has no discovery surface to plug into. What it *does* do is put private "want to watch" information (which can reveal a lot: what you're currently interested in, what genres/directors you're into, what you haven't gotten around to yet) into a state where any future feature built against this flag would broadcast it by default, without the user ever having made that choice.

**Tradeoff acknowledged:** The tradeoff is real: if/when CineLog does build a discovery or profile feature, a `public=False` default means new watchlists start invisible to that feature, and the friction Samiz244 is trying to avoid, "requiring manual privacy toggles", comes right back, because most users won't think to flip a visibility switch they don't know exists. That's a legitimate cost to adoption of any future social feature. But I'd rather pay that cost later, deliberately, when we actually ship a discovery feature and can prompt users to opt in with full context of what "public" means at that point, than default to broadcasting user data today for a feature that doesn't exist yet. Privacy-by-default is also the safer failure mode: if we ship the social feature and `public=False` turns out to hurt engagement, we can flip the default and communicate it; if we ship `public=True` today and it turns out to expose users' data in ways they didn't expect, that's a trust problem we can't easily undo. (The stretch feature I added---an explicit `public` parameter on `add_to_watchlist()`---is meant to make this an intentional, visible choice for callers rather than an invisible default either way.)

## Comment 5 — Sort order
**My position:** I agree with the maintainer and switched `get_watchlist()` from alphabetical (`Film.title.asc()`) to newest-first by date added (`WatchlistEntry.date_added.desc()`). This also makes the watchlist consistent with `get_collection()`, which already sorts `CollectionEntry.date_added.desc()`. Before this change, the two features sorted on completely different axes for no documented reason.

**Reasoning:** A watchlist and a collection serve different mental models, and I think that distinction actually argues *for* the same sort order, not against it. A collection is a historical record (films you've already watched), so "what did I log most recently" (date-added-desc) is the natural way to browse it, and that's what the existing code already does. A watchlist is a queue of intent (films you *haven't* gotten to yet) and the two things a user actually does with a queue are (1) see what's freshest, to decide what's top of mind right now, and (2) work backward to the oldest entry, the film they've been meaning to watch the longest. Alphabetical order serves neither of those tasks; it only helps if you're trying to locate one specific title you already know is on the list, which is a lookup problem, not a browsing problem, and it's not what `GET /watchlist/<user_id>` is for (there's no title/search query param on that endpoint).

**Engagement with reviewer's point:** The maintainer's point that "most users want to see what they added recently" matches exactly what I found when I looked at how `get_collection()` already behaves and reused that pattern rather than inventing a third convention. `Dani-risingBW`'s comment adds the other half of the argument I hadn't fully considered on my own: date order doesn't just serve "what's new," it also serves the opposite direction: finding the oldest untouched entry to finally cross it off, which alphabetical order can't do at all (the oldest addition could start with any letter). Between the maintainer's framing and Dani-risingBW's, I don't see a case for alphabetical that survives; I implemented date-added-desc rather than proposing a third option because the two arguments for it are specific to how a watchlist is actually used, not just "consistency for its own sake."

## PR Description

**What this feature does:** Adds a watchlist to CineLog so users can save films they want to watch later, separate from their `collection` (films they've already watched). It adds a `WatchlistEntry` model, `add_to_watchlist(user_id, film_id)` / `remove_from_watchlist(user_id, film_id)` / `get_watchlist(user_id)` service functions, and three REST endpoints: `GET /watchlist/<user_id>` (list a user's watchlist, newest-first), `POST /watchlist/<user_id>/add` (add a film, with duplicate and nonexistent-film handling), and `DELETE /watchlist/<user_id>/remove` (remove a film).

**Design decisions:**
- **Default visibility:** New watchlist entries default to `public=False` (private). CineLog currently has no discovery/social surface anywhere in the app (no profile pages, no followers, no way to browse another user's watchlist without already knowing their `user_id`), so defaulting to public would expose users' "want to watch" data for a discovery feature that doesn't exist yet. Callers who do want a public entry can pass `public=True` explicitly via the new `public` parameter on `add_to_watchlist()`. Full reasoning in Comment 4 above.
- **Sort order:** `get_watchlist()` returns entries newest-added-first (`date_added.desc()`), matching `get_collection()`'s existing sort order, instead of alphabetical. A watchlist is a queue of intent, and users need to see both what's freshest and work backward to the oldest un-watched entry — alphabetical order supports neither. Full reasoning in Comment 5 above.

**How to manually test:**
1. Start the app: `python app.py` (runs on `http://127.0.0.1:5000`).
2. Create a user and a film, or use the seeded data — first check `GET /films/` to find a valid `film_id`, and note that user creation isn't exposed via API in this starter, so use the test fixtures / a direct DB insert, or `flask shell`, to get a `user_id`.
3. Add a film to the watchlist: `curl -X POST http://127.0.0.1:5000/watchlist/<user_id>/add -H "Content-Type: application/json" -d '{"film_id": "<film_id>"}'` — expect `201` and a JSON body with `"public": false`.
4. Try adding the same film again — expect `409` with an "already on this user's watchlist" error.
5. Try adding a nonexistent `film_id` (e.g. a random UUID) — expect `404`.
6. Add a second film with `"public": true` in the body — expect `201` with `"public": true` in the response (stretch feature).
7. `GET /watchlist/<user_id>` — expect both films back, newest-added first.
8. `DELETE /watchlist/<user_id>/remove` with `{"film_id": "<film_id>"}` for one of them — expect `200`, then re-`GET` to confirm only the other film remains (stretch feature).
9. Run the automated suite end-to-end: `pytest tests/ -v` — all tests (collection + watchlist) should pass.
